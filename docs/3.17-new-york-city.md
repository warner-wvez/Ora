# New York City

957 cameras from NYC DOT, snapshot refreshing every two seconds. The city's own feed,
separate from the state's 511 cameras, shipped as `cameras-nyc.json`. In the sidebar it is
folded into New York's row, and the arrow keys cycle state and city cameras in one
spatial order.

## Where the list comes from

NYC DOT's public camera GraphQL API at `webcams.nyctmc.org/cameras/graphql`, no key, which
also backs 511ny.org. The committed file is a preprocessed copy of that list.

## How images and video are read

The file stores a `camId` per camera and no snapshot URL; the page builds
`https://webcams.nyctmc.org/api/cameras/<camId>/image?t=<now>` at render time, which the
site itself polls every two seconds. No video: NYC's cameras are stills served fast, and
the difference in how live they feel next to Illinois is entirely the backend's cadence,
not the protocol.

## What a camera gives us

Name (usually an intersection), one view.

## Known limits

- Whether a view has a still is the layer's call, not the field's: the snapshot is built
  from `camId`, so a check on the raw `snapshot` field says "no image" for all 957. That
  bug shipped once (2026-07-12) and is why the page asks the layer's `snap` function.
- No builder script in the repo and no health file; the endpoint is polled live.

## Runbook

None. Re-export the GraphQL camera list and regenerate `cameras-nyc.json` in the same
shape.
